# `10a5:a921` 接入记录

一台 HONOR MagicBook（`FMI-XX` / `FMI-XX-PCB`，`product_version M1020`）上的
FPC 指纹，从「设备能枚举、按了没反应」到「正常按压即可注册、验证、锁屏解锁」。
本文只记结论、证据和改法；探索过程见根目录 [README](../README.md)。

| 项 | 值 |
|---|---|
| 传感器 | `10a5:a921`，hwid `0x331`，type 7，64×176，8 bpp，`bcdDevice 0.39` |
| 系统 | Linux Mint 22.3 (Zena)，内核 7.0.0-38-generic |
| 栈 | libfprint 1.94.6 + MR 396 + `patches/`，fprintd 1.94.3 |
| matcher | 闭源 `libfpcbep.so`，md5 `f7136fd774d5208e629bbeaa4974543a`，1,650,656 字节 |

匹配在主机侧完成：传感器只负责成像和按 TLS-PSK 加密上传，解密、比对、模板存储
都在 `libfpcbep.so` 里。

## 实测结果

```

```

| 按压 | 命令 | 结果 |
|---|---|---|
| 右手食指 | `fprintd-verify -f right-index-finger` | `verify-match` |
| 右手中指，第一次 | `fprintd-verify -f right-middle-finger` | `verify-no-match` |
| 右手中指，第二次 | 同上 | `verify-match` |
| 左手食指（未注册） | `fprintd-verify -f right-index-finger` | `verify-no-match` |

中指比食指更需要「按正」，模板本身可用；未注册手指被拒绝，说明补尾没有把
matcher 变成橡皮图章。

## 五个关键判断

改法有很多种可能，下面每个判断都是先拿到证据再改的，顺序不能颠倒——a921 的
差异是叠加的，前一层没通，后一层根本看不到。

### 1. 事件头是小端，不是大端

a900 的驱动按大端解析。a921 上读到的长度是 `0x0a000000` 这种明显字节序反了的
值，状态机随即卡死。把头、以及 16 位字段统一按小端读（`0012`、`0013`）之后，
记录长度才落在合理区间。

### 2. 传感器是 TLS **服务端**，主机要主动发 ClientHello

表现：`fpc_enclave_tls_init_handshake status -1`，EP 0x81 上一个字节都不来。
`libfpcbep.so` 内置的 mbedtls 只编了服务端，根本不会发 ClientHello。

改法是 `LD_PRELOAD` 一个 shim（`tools/fpc_tlsclient.c`，`0016`），接住 blob 的
`mbedtls_ssl_handshake_step` / `_read` / `_write` / `_get_bytes_avail`，用 OpenSSL
跑 TLS 1.2 PSK 客户端，走驱动自己的 `fpc_tls_buff` / `fpc_tls_write_buff` 环。
握手成功后把 blob 的 TLS 状态字（base + `0x196100`）写成 16——这是
`fpc_enclave_process_data()` 唯一认的「可解密」状态。

### 3. 图像消息前缀 24 字节，matcher 要 34

a921 的图像应用消息是 11288 字节 = 24 字节前缀（type 8，抓取 id 在 `0x0c..0x15`）
+ 11264 字节像素。blob 却硬编码像素从 34 开始，于是每张图都错位。

改法与 a900 的 `0009` 相同：在偏移 24 处插入 10 字节空档，总长度加到 11298
（`0018` 在 a921 上打开这段重排）。判断依据是 11288 − 11264 = 24，以及 blob 里
对 34 的硬编码；打开后 `FPC_IMG_DIAG=1` 的追踪能直接看到 gap 被插入。

### 4. 正常按压只覆盖 0..119 行，尾部要补

这是最反直觉的一条。抓帧（`FPC_DUMP_DIR`）看得很清楚：64×176 的帧里，第 0..119
行有指纹脊线，其余整片 `0xff`。闭源 matcher 把空白尾当成「手指没放好」，一律返回
4（`IMAGE_LOW_COVERAGE`），注册永远停在 0/11。

用离线 harness 把同一批真帧按不同变换喂给 matcher，结论明确：

| 变换 | `fpc_tee_enroll` 结果 |
|---|---|
| 原样 | 十张全是 4 |
| 噪声 / 纯色填充 | 6（质量低） |
| 把 0..118 行镜像到 119..175 | 十张全是 1（继续），随后登记 + 识别返回同一 id |

所以改法是在 shim 里做固定映射：第 `y ≥ 119` 行取第 `236 − y` 行，由
`FPC_IMG_FILL=mirror` 开启。注册和验证用同一条映射，畸变一致；被覆盖的只是
真实按压下恒为空白的行，不可能凭空造出脊线。

### 5. 每次采集多一条尾记录，还可能晚到

a921 每次采集发 12 条记录，驱动只读 11 条，第 12 条带着图像消息最后 24 字节。
不读掉它，消息永远差 24 字节，`fpc_enclave_process_data()` 每条记录都回 `-6`。
`0017` 让 a900 已有的 post-drain 逻辑在 a921 上也生效。

还有更隐蔽的一种：这条尾记录可能在 post-drain 超时之后才到，于是落在 dead-pixel
读取里，被当成「长度 12 的错误」直接失败。`0019` 在判错之前先把它交给 enclave
（保持 TLS 序列对齐）并重新读一次。区分两者的依据是事件 id 和长度，所以失败信息
里也把它们打了出来。

## 补丁做了什么

| 补丁 | 改动 |
|---|---|
| `0011` | `id_table` 加 `10a5:a921` |
| `0012` | 事件头按小端解析 |
| `0013` | 16 位字段按小端解析 |
| `0014` | 修 SSM 每条记录推进两次 |
| `0015` | 用 Windows 的方式下发主机密钥 |
| `0016` | TLS 客户端 shim + 应用消息头改成大端 |
| `0017` | 读掉每次采集的尾记录 |
| `0018` | a921 打开图像消息重排（10 字节 gap） |
| `0019` | 容忍晚到的 header-only 记录 |
| `0020` | `FPC_IMG_DIAG=1` 追踪重排是否命中 |
| `0021` | 无图像记录的 `-6` 从 warn 降为 debug |

`0001`–`0010` 是 a900 工程原有的改动，`build.sh` 按顺序全部应用。

一条教训：`0018`–`0020` 起初只存在于工作树，没有做成补丁；`build.sh` 会
`git checkout -- .` 重置源码，行为就悄悄变了。现在它们都在 `patches/` 里，重建
之后与部署的 `.so` 一致。

## 部署与验证

`sudo ./install.sh` 装三样东西：`/opt/fpc-a921/lib`（libfprint + blob + shim）、
一条 udev 规则、一个 fprintd drop-in。发行版 libfprint 不动，只有 fprintd 看到
补丁版：

```
Environment=LD_LIBRARY_PATH=/opt/fpc-a921/lib
Environment=LD_PRELOAD=/opt/fpc-a921/lib/libfpc_tlsclient.so
Environment=FPC_IMG_FILL=mirror
```

验证顺序（一次只开一个客户端，别和图形界面抢设备）：

```bash
fprintd-enroll                          # 正常按压，约 11 个样本
fprintd-verify -f right-index-finger    # 必须 match
fprintd-verify -f right-index-finger    # 用未注册的左手按，必须 no-match
```

`finger-not-centered` 每次都出现时，先确认镜像补齐生效：

```bash
systemctl show fprintd -p Environment | tr ' ' '\n' | grep IMG_FILL
```

## 已知边界

- 分界行（119）是在这个按钮开槽、这种按法下测的。接触面明显更小的按压仍可能被判
  4，驱动会让重试，但不会伪造效果。
- 中指模板容错比食指低，偶尔需要第二次按压；这是 matcher 的评分，不是驱动 bug。
- 反例只测了左手食指一只手指，足以证明不误接受，但不足以量化整体的跨指误接受率。
- fprintd 1.94.3 在客户端 `Claim` 超时后会留下设备占用，下一个客户端静默拿不到
  设备；`systemctl restart fprintd` 清除即可。
