# `10a5:a921` bring-up — HONOR MagicBook X16 Plus 2024

This is the record of taking one machine from "the sensor enumerates and then
does nothing" to "a normal press enrolls and verifies". Everything below was
measured on the hardware, not inferred from the Windows driver.

Machine: HONOR `FMI-XX` (board `FMI-XX-PCB`), Linux Mint 22.3, kernel 7.0.0,
fprintd 1.94.3, libfprint 1.94.6 + MR 396 + `patches/`.

```
Bus 001 Device 004: ID 10a5:a921 FPC FPC Sensor Controller
hwid 0x331, type 7, 64 x 176, 8 bpp, bcdDevice 0.39
```

The sensor is match-on-host: it captures and encrypts, the closed
`libfpcbep.so` does the TLS server side, the matching and the template store.

## What a900 support did not cover

MR 396's `fpcmoh` driver drives the a900. The a921 differs in six places that
each stop the driver on its own:

| # | difference | symptom without the fix | patch |
|---|---|---|---|
| 1 | id `10a5:a921` missing from `id_table` | `No driver found for USB device` | `0011` |
| 2 | event headers and 16-bit fields are little-endian | lengths like `0x0a000000`, state machine stalls | `0012`, `0013` |
| 3 | the SSM advanced twice per record | every other record consumed twice, timeouts | `0014` |
| 4 | the host key is provisioned the Windows way | handshake never starts | `0015` |
| 5 | the sensor is the **TLS server** | `fpc_enclave_tls_init_handshake status -1`, silence on EP 0x81 | `0016` |
| 6 | a trailing 12-byte record follows every capture | fatal error after a sample, enrollment aborts | `0017` |

and three more that only show up once the transport works:

| # | difference | symptom without the fix | patch |
|---|---|---|---|
| 7 | the image message needs the a900's gap, but the a921 never enables it | every sample scored unusable, enrollment progress sticks at 0/11 | `0018` |
| 8 | a header-only record can arrive after the post-drain timeout | `len 12 err!`, operation aborted mid-enrollment | `0019` |
| 9 | the enclave answers `-6` for every image-less record | two warnings per press in the journal, looks like a broken sensor | `0021` |

`0020` adds `FPC_IMG_DIAG=1` tracing to the relayout, which is what made item 7
visible instead of guesswork.

And two differences in the application message that the a900 fix-up
(`0009`) does not know about:

- the message header is little-endian and has to be rewritten to big-endian
  before the blob parses it (`patches/0016`, `fpc_img_msg_relayout`);
- the image message carries a 24-byte prefix (type 8, total 11288, capture id
  at `0x0c..0x15`), while the blob hardcodes 34 bytes and expects the pixels at
  24. The driver opens a 10-byte gap at offset 24 and bumps the total to 11298.

## The TLS problem, and the shim

The blob's bundled mbedtls is built server-only. On the a921 the sensor refuses
to speak until the host sends a ClientHello, and nothing in `libfpcbep.so` can
produce one: `mbedtls_ssl_handshake_step` returns
`MBEDTLS_ERR_SSL_BAD_INPUT_DATA` for a client context.

`tools/fpc_tlsclient.c` is `LD_PRELOAD`ed into fprintd and interposes the blob's
`mbedtls_ssl_handshake_step` / `_read` / `_write` / `_get_bytes_avail` for the
blob's global ssl context (base + `0x1960f8`). It runs an OpenSSL TLS 1.2 PSK
client (cipher `0x00a8`, PSK-AES128-GCM-SHA256, identity `Disum PSK`) over the
same `fpc_tls_buff` / `fpc_tls_write_buff` rings, and sets the blob's TLS state
word at base + `0x196100` to 16 (handshake over) when OpenSSL reports success.
16 is what `fpc_enclave_get_tls_status()` maps to "complete" and what
`fpc_enclave_process_data()` gates on.

## The coverage problem

With TLS and the message layout fixed, every sample came back as result 4,
`IMAGE_LOW_COVERAGE`, and enrollment could never finish. Dumping the frames
(the shim writes every >1000-byte application message when `FPC_DUMP_DIR` is
set) shows why: a normal press on this button images rows 0..~119 of the 176-row
frame; everything below is exactly `0xff`. The vendor matcher treats the blank
tail as "finger not on the sensor", while the Windows driver does not.

Filling the tail is enough to change the verdict. Measured by replaying the same
ten captured frames into `libfpcbep.so` offline (`tools/fpc-offline-harness.c`
from the investigation, fed through a fake `mbedtls_ssl_read`):

| frame transform | `fpc_tee_enroll` result |
|---|---|
| identity | 4 on all ten |
| noise / constant fill | 6 (low quality) |
| mirror rows 0..118 into 119..175 | 1 on all ten, then enroll + identify returns one id |

The shim does exactly that mirror when `FPC_IMG_FILL=mirror` is set: row `y`
for `y >= 119` takes row `236 - y`. The mapping is fixed, so enrollment and
verification distort the frame the same way, and only the rows that are blank
in practice are overwritten.

## Result on this machine

```
fprintd-DEBUG: Device reported enroll progress, reported 11 of 11 have been completed
fprintd-DEBUG: fpc_store_template_db: blob_size 14508
ENROLL RESULT: SUCCESS
VERIFY RESULT: MATCH
```

Measured after enrollment through `fprintd-enroll` / the Mint GUI, one client at
a time, `fprintd-verify -f <finger>`:

| press | expected | result |
|---|---|---|
| right index, `-f right-index-finger` | match | `verify-match` |
| right middle, `-f right-middle-finger`, 1st try | match | `verify-no-match` |
| right middle, 2nd try | match | `verify-match` |
| left index (not enrolled) | no match | `verify-no-match` |

So both fingers work — the middle one just needs a second press more often than
the index — and an unenrolled finger is rejected, i.e. the mirrored tail does
not turn the matcher into a rubber stamp.

The deployed stack is `/opt/fpc-a921/lib` (libfprint, `libfpcbep.so`, the shim)
plus one fprintd drop-in:

```
Environment=LD_LIBRARY_PATH=/opt/fpc-a921/lib
Environment=LD_PRELOAD=/opt/fpc-a921/lib/libfpc_tlsclient.so
Environment=FPC_IMG_FILL=mirror
```

Only fprintd sees the patched build; the distro libfprint is untouched.

## Reproducing on another a921

```bash
./get-blob.sh            # libfpcbep.so, md5 f7136fd774d5208e629bbeaa4974543a
./build.sh               # libfprint 1.94.6 + MR 396 + patches/*.patch
sudo ./install.sh        # /opt/fpc-a921/lib + udev rule + fprintd drop-in
fprintd-enroll           # normal presses, ~11 accepted samples
```

If enrollment reports `finger-not-centered` on every sample, the mirror fill is
not active — check `systemctl show fprintd -p Environment | grep IMG_FILL`.

## Debugging knobs (all in the shim, all off by default)

| variable | effect |
|---|---|
| `FPC_TLS_TRACE=1` | byte counts on both sides of the OpenSSL BIO, per record |
| `FPC_DUMP_DIR=/tmp/frames` | write every >1000-byte application message to `img-NNN.raw` |
| `FPC_IMG_FILL=mirror` | enable the tail fill (required for enrollment) |

`G_MESSAGES_DEBUG=all` in a fprintd drop-in turns on the driver's `fp_dbg`
lines, including the per-sample `fpc_tee_enroll -> N, remaining M` verdicts.

## Mint integration

Nothing above is Mint-specific; this is what the desktop does with it.

**Enrollment / management.** The Mint fingerprint app (`fingwit`) works, but it
claims the device on startup. If another client was killed mid-claim, fprintd
1.94.3 keeps the claim and the app opens no window (`Device was already
claimed`). `systemctl restart fprintd` clears it — the app is not broken.

**Lock screen and login.** Both go through lightdm, whose PAM stack includes
`common-auth`, so two lines in `/etc/pam.d/common-auth` are all the
integration there is:

```
auth  [authinfo_unavail=1 default=ignore] pam_fingwit.so
auth  [success=2 default=ignore]          pam_fprintd.so max-tries=3 timeout=15
```

`max-tries` is the number of presses before PAM falls back to the password;
with the default of 1 a single imperfect press sends you straight to the PIN.
Keep it at 3–5. The same stack serves `sudo`, so `sudo` also accepts a finger.

The one rough edge: Mint's lock screen is slick-greeter 2.2.6, which has no
fingerprint UI (`strings /usr/sbin/slick-greeter | grep -i finger` returns
nothing). PAM completes on match — the journal shows
`gkr-pam: no password is available for user`, i.e. no password was typed — but
the greeter does not submit the session by itself, so one keypress (Enter) is
needed after the sensor LED confirms. That is a greeter limitation, not a
driver one; a locker that unlocks directly on PAM success (for example
`xfce4-screensaver`, ~260 kB download / 1.3 MB installed) is the way around it
if the extra keypress matters.

**`pam_fingwit.so` needs a system python.** The module execs `python3` from
`PATH`. With a conda environment first in `PATH` that python has no `gi`, so
the module prints a traceback before falling through to `pam_fprintd`. It is
harmless (`pam_fingwit` only gates, it never authenticates by itself and always
returns `PAM_IGNORE` here) but noisy; either drop the line or make sure
`/usr/bin` comes first for the greeter.

## Known limits

- The split row (119) is measured for this button slot and a normal press. A
  press with a much smaller contact patch can still be scored 4 and has to be
  repeated; the driver asks for a retry instead of failing.
- Cross-finger discrimination with the mirrored frame: an unenrolled left index
  is rejected, and re-enrolling the same finger is reported as duplicate. The
  mirror only overwrites rows that are blank on every real press, so it cannot
  invent ridge detail; no false accept has been observed, but only one finger
  was used for the negative test.
- fprintd 1.94.3 can be left holding a device claim after two clients (the GUI
  and `fprintd-enroll`) race; `systemctl restart fprintd` clears it. Operate one
  client at a time.
